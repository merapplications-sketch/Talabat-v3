## 1. مطابقة المضيف — بوابة إلزامية قبل أي كتابة

الأدلة السابقة `docs/pilot-20261105/operations/external-acceptance/HOST-CONTRACT-DIFF.json` أثبتت غياب20 دالة للمرشح عن metadata المضيف؛ ليست مقارنة أجسام كاملة. أضيف تصحيح التوزيع بعدها. لا يجوز اعتبار المضيف مطابقاً أو تطبيق سلسلة SQL فوقه عميانياً.

مسؤول Supabase يوفّر تصديراً موجوداً ومنقحاً للمخطط والدوال والتواقيع والسياسات والحراس والمنح الفعلية، وإعدادات Auth/SMTP/redirects/REST/Realtime/Storage. لا كلمات مرور ولا مفاتيح في المستودع. يملأ فريق التطبيق `host-input.example.json` ويشغّل `python release/pilot-candidate/compare-host.py <export.json>` محلياً. الفاحص يقارن بصمات الملفات المقابلة/الترقيات المثبتة ويُبقي إعدادات الخدمات والاختبار الميداني أبواباً مستقلة؛ لا يدّعي مطابقة SQL بناءً على أسماءRPC فقط.

التصدير الكامل لم يُتح هنا؛ لذلك اختيار baseline إنتاجي دقيق وترقية إنتاجية قابلة للتنفيذ **محجوبان**. ملفات bootstrap وpatch-a داخل tests مصدر معمل فقط وليست برنامج تهيئة للإنتاج. baseline منشور قديم `ca8808dd` دليل تاريخي، وليس نقطة رجوع إنتاجية معتمدة اليوم.

## 2. ترتيب الترقية المقترح

1. تثبيت نسخة الملفات والإعدادات وبصمة مخطط الوجهة، وتحديد آخر نسخة تشغيل فعلية معروفة. منع بدء طلبات جديدة أثناء نافذة التغيير بعد إذن مستقل؛ معالجة الطلبات الجارية وفق خطة التشغيل.
2. نسخة PostgreSQL متسقة وملفاتStorage مع manifest/baselines، وإثبات فك تشفيرها على وجهة معزولة، وحفظ سجل المراقب/outbox وإيصالاته. النسخة السابقة الاصطناعية لا تغني عن النسخة التشغيلية.
3. على نسخة معزولة من baseline مطابق: طبّق حصراً المراحل غير الموجودة بترتيب `upgrade_order` في manifest. لا إعادة تشغيل رقعة موجودة، ولا ضم `admin_finance_safe_hold` مع التصحيح، ولا تفعيل patch38/40 أو الطرق الداخلية.
4. السلسلة: finance integrity ثم receipts ثم ملفاتpilot حسب الترتيب المعلن، وآخرها cash allocation. لا دمج معاملات BEGIN/COMMIT داخل معاملة وهمية؛ كل مرحلة لها تحقق ونقطة توقف. أخفق أي شرط: أوقف المراحل التالية.
5. اضبط حصة المنصة الفعلية صراحة بمرجع إعداد، دون backfill للطلبات السابقة. المعمل يختبر5 وصفر فقط؛ لا تنقل قيمDEMO أو حساباتDEMO أو اتفاقاتها إلى المضيف.
6. اربط حزمة الواجهات الموافقة بالخادم نفسه. النسخة المالية4 مطلوبة لتنفيذ التسوية؛ تشغيل واجهات جديدة فوق خادم أقدم لا يغلق القبول. مسار الكاش كامل المقبوض يبقى ممنوعاً للتسويات الجديدة.
7. نفّذ فقط تحقق الفروق على الوجهة المعزولة؛ اكتمال فحوص المضيف والبريد والمناوب والأجهزة شرط منفصل. تفعيل أي وجهة إنتاجية يحتاج تكليفاً لاحقاً، وغير منفذ في هذه الدفعة.

## 3. الرجوع

- قبل أول كتابة جديدة: إلغاء نافذة التغيير والعودة إلى ملفات baseline المطابقة، واستعادة النسخة السابقة على هدف **منفصل** والتحقق منها قبل أي تبديل وجهة. لا كتابة فوق أرصدة حيّة في هذه الدفعة.
- بعد وجود طلبات بتوزيع مثبت أو إيصالات جديدة: لا حذف أعمدة التوزيع، ولا استعادة `cash_balances/finance_execute` التي تجمع المقبوض. هذا يعيد عيباً محاسبياً. أوقف القبول والتنفيذ المالي للمراجعة؛ احفظ كل الأحداث الحديثة وصالحها، ثم إصلاح أمامي أو خطة استعادة تعتمدها المالية والمضيف.
- rollback للواجهة وحده لا يكفي إذا كانت لا تفهم حساب الحصة. أبقِ الحراس الخادمية والتوزيعات والإيصالات غير القابلة للتعديل. آخر تسليم محاسبي صالح للمرشحb2f84d8؛ ليس وعداً بأنه منشور.
- سجل المراقب وoutbox وإيصالات وصول القناة تبقى معاً، مع نفس معرفات الأحداث؛ لا تمسحها لتجاوز إعادة المحاولة.

## 4. التشغيل المعزول والرابط

`bash tests/pilot/cash/run.sh` هو المدخل الموحد للواجهات الأصلية عند توافرDocker؛ يعرضها على127.0.0.1:8080 معAuth/REST/PostgreSQL محلية. لا تُرفع HTML الخام إلى استضافة عامة: talabat-core.js الخام يحمل عنوان الخدمة الأصلية، والجسر المعزول وحده يعيد توجيهه إلى المعمل.
