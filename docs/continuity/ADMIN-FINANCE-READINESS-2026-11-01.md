# TALABOT — جاهزية إصلاح الإدارة والمالية

1 نوفمبر 2026، توقيت دوشنبه. أساس الاستئناف `6d2132945743ad1b93ac2f830da66f0ea17bd45f` على `fix/admin-finance-20261101`؛ قرئ السجل §60 وحُفظ إغلاق إسناد 622fc108 ضمن نطاقه. منفذ واحد. الحي: قراءة فقط؛ لم تُستدعَ أي حركة مالية أو Edge Function، ولم تتغير حسابات/صلاحيات/بيانات/SQL حي، ولا نشر أو دمج main.

## الحكم الحالي

**جرد الخادم الفعلي ومقارنته مكتملان ضمن نطاق الوصول المالي للعميل في هذه اللقطة. الرقعة متوافقة محلياً مع البنية الفعلية بعد إغلاق نقصين إضافيين في ACL؛ ليست منشورة أو مطبّقة.** لا توجد الآن عضويات موظفين في `staff_members` بحسب عدّ مجمّع بلا أسماء؛ تطبيق الرقعة سيوقف التنفيذ المالي الإداري لكل الحسابات حتى تفويض محاسب بإجراء منفصل ومصرح به. دور المدير لا يعوّض التفويض.

جاهزية المصدر/المعمل لا تعني جاهزية تشغيل مالي حي فوراً: يبقى التفويض التشغيلي الصريح، وإصدار متزامن للواجهة والخادم، وقبول iPhone/Safari وحساب المحاسب الفعلي. الإيصال ودفتر الصرف والتنبيهات الدائمة بنود مستقلة غير مكتملة.

## ما جُمع حياً بالقراءة فقط

المشروع تحقق باسمه Talabat ومعرفه `dzydscryrnahnneydnry`، PostgreSQL **17.11**. استُخدمت استعلامات SELECT على الكتالوج، وتعريفات مصدر Edge للقراءة فقط؛ لم تُنسخ سجلات أشخاص أو مبالغ أو رسائل أو مواقع أو أسرار.

- **119 دالة public** بالتواقيع والوسائط/القيم الافتراضية والنتائج والتعريف والمالك/SECURITY DEFINER وACL وEXECUTE الفعلي لـanon/authenticated. لا أسماء متعددة التعريف في اللقطة؛ لا overload إضافي للتسوية أو التعديل. `finance_private` غير مثبت.
- **36 جدولاً و14 تسلسلاً**؛ أنواع الأعمدة والهوية والقيم الافتراضية ومنح الجداول والأعمدة الصريحة والفعالة، PUBLIC والأدوار الموروثة، و**44 سياسة RLS و34 trigger و187 قيداً و88 فهرساً**. لا views في public.
- الأدوار وعضوياتها وINHERIT/SET وBYPASSRLS وdefault ACL. لا دور موروث أعلى لـanon أو authenticated في اللقطة؛ PUBLIC لا يملك إنشاء كائنات public. الجداول المالية لديها RLS وسياسات قراءة فقط في مساراتها المباشرة، رغم وجود بعض منح الجدول الأوسع.
- جرد المخططات لم يجد مخطط تطبيق مخصصاً آخر؛ لا `cron.job`. فُحص مصدر Edge للدالتين route وroute-، دون استدعائهما: تحجزان/تسويان ميزانية الملاحة فقط، ولا تستدعيان قبضاً مكتبياً أو محفظة. لم تُقرأ قيم البيئة أو مفاتيح الخدمة.
- عدّ RBAC مجمّع: **0 صف في staff_members**، لا تعيين حساب وهمي أو إنشاء تفويض حي.
- بصمة تعريفات الـ119 في نهاية الجمع طابقت الملفات المحفوظة: `ed917103ede328ad16f42a23f3c8f2e8`. هذا يؤكد استقرار التعريفات خلال الجمع، ولا يزعم أن الاستعلامات المتعددة كلها transaction snapshot واحدة.

[فهرس الأدلة والبصمات والجرد](admin-finance-readiness/inventory-manifest.json)؛ الاستعلام الأصلي والتوقيت/المشروع محفوظان داخل ملفات الجرد. استجابت أداة القراءة أولاً بنجاح لكن تحليل غلاف النص فشل؛ صُحح الحفظ وأعيدت القراءات المحددة. لا كتابة حية غامضة أو موافقة معلقة نتجت عن ذلك.

## مسارات الكتابة وحكم الصلاحيات

| المسار المثبت | حكم الحي | حكم الرقعة الحالية |
|---|---|---|
| settle_driver_cash(uuid) | has_perm('finance') يقبل المدير دون تفويض مستقل؛ SUM ثم UPDATE | نقطة قديمة ترفض التنفيذ؛ finance_execute يفرض عضوية finance نشطة ومفتاحاً وقفل المعاملة |
| wallet_adjust(uuid,numeric,text) | has_perm('finance')، يكتب created_by؛ المدير يقبل ضمناً | نقطة قديمة ترفض؛ التعديل اليدوي يمر بالأمر المحمي وحده |
| كتابة orders/wallet_entries مباشرة | RLS وسياسات القراءة تمنع DML المباشر؛ وجود ACL واسع وحده ليس إثبات تجاوز API | سحب UPDATE للطلبات وDML للمحفظة والأعمدة/PUBLIC؛ لا تغيير لمسار التحصيل التشغيلي |
| TRUNCATE orders/wallet_entries/audit_log | منحة authenticated موجودة فعلياً، وTRUNCATE لا تقيده RLS | **أغلق في الرقعة** بسحب TRUNCATE من PUBLIC/anon/authenticated |
| إعادة ضبط أرقام orders/wallet_entries/audit_log | UPDATE على التسلسلات متاح، ومنها wallet_entries_id_seq لـanon وauthenticated | **أغلق في الرقعة** بسحب UPDATE لتسلسل id دون حذف التاريخ أو تغيير أرقامه |
| inherited grants غير متوقعة عند الإصدار | لا توجد عضويات أعلى للعميل في اللقطة | guard يرفض المعاملة كلها إذا بقيت صلاحية كتابة/محو/تعديل تسلسل عبر الإرث؛ لا تعديل تلقائي لأدوار غير معروفة |
| deliver_order(bigint,numeric,text,text) | السائق المكلّف، pickedup، قفل طلب وتحقق نقد/صورة | التعريف ومنحة EXECUTE بقيَا كما هما؛ ليس قبضاً مكتبياً |
| ticket_set_status وتعويض الدعم | support وفق حدود الطلب، يكتب refund/created_by | بقي كما هو؛ ليس مسار تصحيح محفظة يدوي مفتوحاً بلا سبب. لا إعادة حوكمة تعويض الدعم ضمن هذا التكليف |
| place_order / trg_wallet_return / trg_loyalty | دفع محفظة وإرجاع إلغاء وكاش باك مرتبط بالطلب | بقيت التعريفات كما هي؛ ليست قبضاً/صرفاً مكتبياً؛ لم تتغير الأسعار أو سياسات المقاصة |
| staff_set / staff_remove | المدير يدير تفويض موظف، والكتابة المباشرة لجدول العضوية ممنوعة | حوكمة التفويض القائمة بقيت؛ staff_set يرفض ملفاً بدور admin، فلا تفترض منح المدير نفسه تلقائياً |

منح TRUNCATE والتسلسل أثبتت في المعمل بهوية authenticated على البنية المنسوخة ثم رفضت بعد الرقعة؛ **ليست حادثة حيّة مثبتة**. PostgREST العادي لا يقدم endpoint لـTRUNCATE/setval؛ الحكم عن صلاحيات دور قاعدة البيانات ومسارات الوصول إليه، لا ادعاء أن زر التطبيق مكّن المحو. service_role ومالك قاعدة البيانات يظلان سلطات موثوقة ذات امتياز؛ لا نزعم أن شرط المحاسب يقيد مدير قاعدة البيانات أو مفتاح الخدمة المسرب.

الجرد المحلي يحدد 25 تعريفاً كاتباً للجداول المرتبطة، مع تعريفاتها كلها متاحة للتدقيق. لم يوجد writer آخر لـcash_settled_at أو kind=adjust في تعاريف public المثبتة غير المسارين المستبدلين. SQL الديناميكي المكتشف في check_promo يقرأ happy_hour_pct ولا يكتب المال. لا نعيد تأويل grants لتصحيح السجل أو نعبئ إسناداً تاريخياً جديداً.

## توافق التطبيقات القديمة

| التركيبة | الحكم |
|---|---|
| التطبيق القديم + الخادم الحالي | يبقى التنفيذ القديم كما هو؛ لا تُنسب إليه حمايات الرقعة |
| الواجهة الحالية من فرع الإصلاح + الخادم الحالي | ترفض الكتابة عند غياب عقود v2؛ بعض قراءات الإسناد/المحاسب غير متاحة. ليست تركيبة تشغيل مالي |
| التطبيق القديم + الرقعة | استدعاءات settle_driver_cash وwallet_adjust دون مفتاح ترفض عمداً. لا fallback ولا تعديل بيانات؛ يلزم تنسيق تحديث الإدارة |
| الواجهة الحالية + الرقعة المحدثة + محاسب مفوض | العقود متطابقة مع تواقيع وأنواع الخادم الفعلية، واجتازت التطبيق والكتابة المحمية في معمل البنية الحقيقية؛ قبول تشغيل الجهاز والخدمة الحية لم يُنفذ |

قورنت استدعاءات main وintegration/customer-v80-current الموجودتين بالمستودع: تستخدمان النقطتين القديمتين، ولا يوجد فيها تحديث مباشر للطلبات أو المحفظة في ملفات التشغيل المفحوصة. سحب UPDATE لا يغير تحديث ملف السائق في profiles. تعريفات deliver_order وticket_set_status وplace_order وtrg_wallet_return وtrg_loyalty لم تتغير بعد تطبيق الرقعة محلياً. لا ندعي من المستودع معرفة كل عميل خارجي غير محفوظ.

## التسليم والمتبقي

- [خطة الإصدار والرجوع الآمن](admin-finance-readiness/RELEASE-ROLLBACK-AR.md): لا تعليمات تنفيذ تلقائي؛ الرقعتان داخل sql/proposed فقط. الرجوع لا يعيد endpoint القديم غير المحمي ولا يمحو ledger/commands أو يعكس مبالغ مؤكدة.
- [تجربة وقبول iPhone](admin-finance-readiness/IPHONE-ACCEPTANCE-AR.md): ما يمكن تجربته الآن اصطناعياً وما ينتظر إصداراً منسقاً، دون تحويل QA Chromium إلى قبول Safari.
- تبقى معرفة كل عميل خارجي/جلسة privileged خارج حدود كتالوج قاعدة البيانات؛ إعداد exposed schemas لم يرجع عبر إعدادات دور القاعدة، ولم يغيره هذا العمل. الرقعة تلغي USAGE/EXECUTE الخاص للعميل ولا تعتمد على إخفاء finance_private في الإعداد وحده.
- **موانع التشغيل الفعلية:** لا نشر/تطبيق مصرح ضمن هذا التكليف، ولا محاسب مفوض فعلياً حالياً، ولا قبول iPhone/Safari أو جلسة محاسب حي. هذه ليست نواقص جرد public السابقة؛ الجرد أُنجز فعلياً.
- **مستقل وغير مكتمل:** كاتب إيصال التسوية، دفتر الصرف وإثباته وصافي المستحقات، والتنبيهات الدائمة؛ لا مقاصة أو قبض جزئي أو اعتماد صرف مفترض، ولا تفعيل ماليات v60/v61/patch38.
