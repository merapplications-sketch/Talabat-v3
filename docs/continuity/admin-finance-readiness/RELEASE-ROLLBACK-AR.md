# إصدار منسق ورجوع آمن — خطة غير منفذة

## قبل الإصدار

1. يلزم تكليف منفصل لتطبيق الرقعة/النشر/تفويض محاسب. هذا التسليم للقراءة والمعمل فقط.
2. أعد جرداً محدداً بالقراءة فقط وقت الإتاحة، وقارن تعريفات وتواقيع المسارين القديمين والأنواع والـACL/RLS والعضويات بهذه اللقطة. إن تغير شيء مؤثر، راجعه؛ لا تعتمد MD5 قديماً كضمان دائم.
3. تحقق من حساب محاسب صريح ونشط. الجرد الحالي: staff_members خالٍ؛ المدير وحده سيُرفض. استخدم حوكمة تفويض الموظفين القائمة بعد تصريح المالك، دون إنشاء حساب وهمي أو تغيير دور مدير لتجاوز الرفض.
4. احفظ نسخة البنية والـACL وتعريفات الوظائف ونسخة الواجهة المنشورة، مع نقطة استعادة البيانات وسياسة احتفاظ مأذونة. ملفات هذا التسليم كتالوج وليست backup لبيانات المشروع.
5. اختر نافذة يتوقف فيها القبض المكتبي وتعديل المحفظة اليدوي مؤقتاً، مع إبلاغ المستخدمين خارج هذا التكليف؛ لا تستأنف طلباً مالياً غير محسوم تلقائياً. لا تتوقف رحلة السائق التشغيلية بلا داعٍ.

## الإصدار عند تصريح لاحق

1. طبّق `sql/proposed/admin_finance_integrity_20261101.sql` كمعاملة واحدة. guard الإرث يرفض المعاملة إن بقي منح غير متوقع؛ لا تحذف guard أو توسّع الأدوار لتجاوز الرفض.
2. تحقق بالقراءة من تواقيع finance_* ونسخة capability=2 والـACL/RLS، ومن بقاء الدوال التشغيلية كما في الجرد. قراءة capability وحدها ليست كافية.
3. انشر الواجهة المتطابقة على الوجهة المعتمدة في ذلك التكليف؛ العميل القديم يرفض المسارات المالية القديمة بعد الرقعة عمداً. لا تنشر الواجهة وحدها مع خادم قديم كتجربة مالية مكتملة.
4. نفّذ قبول iPhone/session المحاسب في بيئة مصرح بها أولاً. المصادقة والاستعلام عن النتيجة والقراءات يمكن فحصها دون حركة حية؛ أي قبول كتابة مالية حية يحتاج تفويضاً خاصاً وسيناريو مضبوطاً، وغير مسموح به هنا.
5. لا تفعّل مقترح B أو إيصالاً أو صرفاً أو تنبيهات غير مكتملة ضمن هذا الإصدار. لا تغير التسعير أو التتبع/الخرائط/المحادثة.

## الرجوع/الاحتواء عند خلل مؤثر

الهدف إيقاف كتابة مالية جديدة مع حفظ كل أثر مؤكد. **ليس عكساً تلقائياً للمبالغ.**

1. عند تكليف رجوع مصرح به، استخدم `sql/proposed/admin_finance_safe_hold_20261101.sql`: يعطل capability ويسحب EXECUTE من finance_execute. لا يستبدل الرصيد أو المحفظة أو created_by أو cash_settled_at أو finance_private.commands.
2. سحب EXECUTE يمنع الطلبات الجديدة، لكنه لا يلغي معاملة بدأت بالفعل. انتظر حسم الطلبات الجارية، وافحصها قراءة عبر finance_command_status لنفس المنفذ. غياب النتيجة لا يثبت الرجوع. لا تعِد إرسال حركة ولا تحذف أو تعكس سجلاً تلقائياً.
3. يمكن إرجاع ملفات الواجهة المحفوظة إذا تطلب عيب العرض ذلك، مع بقاء الكتابة المالية متوقفة. لا تستعد settle_driver_cash أو wallet_adjust القديمتين اللتين تقبلان المدير ضمناً؛ المستخدم القديم سيبقى مرفوضاً مالياً حتى الإصلاح المنسق.
4. أبقِ دوال القراءة والاستعلام والمخطط الخاص وتاريخ الأوامر. لا DROP SCHEMA ولا TRUNCATE ولا إعادة منح صلاحيات واسعة، ولا محو سجل لجعل النسخ تبدو متطابقة.
5. راجع السبب وأصلحه على فرع معزول. إعادة تشغيل التنفيذ تتطلب حسم العمليات المعلقة وإعادة مطابقة الواجهة والرقعة وقبول المتأثر، ثم تفويض الإتاحة. لا يفترض ملف الرجوع إذناً بالنشر أو الصرف.

وضع safe hold اختُبر محلياً على البنية الفعلية: capability=false، الطلب المباشر مرفوض، وإثبات الأمر السابق محفوظ. لا استدعاء أو ترحيل حي جرى في هذه الجلسة.
