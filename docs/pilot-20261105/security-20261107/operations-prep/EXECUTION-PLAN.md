## 1. بريد الاستعادة

**الموجود:** مسار الاستعادة في الواجهة، قائمة رجوع محددة، SMTP مخصص غير مفعّل. أدلة المزوّد في provider-followup؛ لا نعيد قراءة الإعدادات الثابتة. خدمة البريد الافتراضية مقيّدة بعناوين فريق المشروع وليست خدمة إنتاج مضمونة. لا إضافة عضو للمنظمة لتجاوز هذا القيد.

**ما أنجزته:** اختبار دوال الاستعادة الفعلية من المصدر، مع بديل محلي لـAuth وDOM: بريد غير صالح لا يرسل، توحيد البريد، الرجوع دون query/hash، النقر المكرر ينتج طلباً واحداً، الاستجابة الناجحة عامة، الخطأ الشبكي يسمح بإعادة يدوية، 429 لا يكرر آلياً، اختلاف كلمتي السر لا يكتب، نجاح التغيير يطلب خروجاً عاماً، فشل التغيير لا يدخل التطبيق، وفشل الخروج يظهر تحذيراً. اختبار منفصل يحافظ على اختلاف متطلبات استعادة الزبون والإدارة. لا إرسال رسائل ولا تغيير كلمات السر.

**الإجراء الجاهز بعد القرار:** حساب اصطناعي منفصل فقط؛ طلب واحد من الواجهة، حفظ وقت الطلب ومعرّف الرسالة دون محتواها السري، إثبات وصولها وفتح رابطها على النطاق المعتمد، تغيير كلمة حساب الاختبار الجديد عبر الإدخال الآمن، الدخول الجديد، اختبار إعادة استخدام الرابط وانتهائه، ثم الجلسة القديمة. حساب الإدارة الذي عليه MFA يجب ألا يتجاوز العامل بعد الاستعادة. فقدان العامل مسار آخر لا يغلقه نجاح استعادة كلمة السر.

**قرار المالك الأدنى:** الإذن باستعمال صندوق تملكه لاختبار رسالتين كحد أقصى، وتحديد عنوانه فقط (ليس كلمة سره). الخيار الأقل تجهيزاً: صندوق مستخدم موجود أصلاً في فريق Supabase، دون تغيير عضويات. إن لم توافق على ذلك، اختر صندوق اختبار مخصصاً ومزوّد SMTP معتمداً؛ سأجهّز الربط وأفحصه بعد اختيارك، ولا يلزم أن تجهّز الاختبارات بنفسك.

**أين تحفظ السر إن احتجنا SMTP:** افتح https://supabase.com/dashboard/project/fsvrsvqfknogwmhccera/auth/smtp ثم Enable custom SMTP؛ أدخل بيانات المزوّد في لوحة Supabase نفسها: sender وhost وport وusername وpassword، ثم Save changes. لا تنفّذ ذلك قبل اعتماد المزوّد والكلفة. لا ترسل password أو رابط الاستعادة أو رمزاً بالمحادثة. فتح البريد يتم بحسابك عبر الدخول الآمن.

**الكلفة/الوصول:** لا خدمة مدفوعة للحزمة المحلية. كلفة SMTP الجديد غير محددة حتى اختيار المزوّد؛ لا نفترض أنه مجاني. نجاح صندوق الاختبار لا يثبت تسليم البريد إلى كل المستخدمين أو السمعة وSPF/DKIM/DMARC.

## 2. نسخ DB والملفات والاستعادة المنفصلة

**الموجود:** الخطة الحالية لا تتضمن نسخ مشروع مجدولة؛ الأدلة وSQL ليست نسخة بيانات. نسخ DB لا يتضمن بايتات Storage. لم نجد هنا docker أو psql أو pg_dump، ولا اتصال تصدير مباشر محفوظ أو هدف استعادة معتمد. الأدوات المتصلة تتيح SQL، ولا تتيح تصديراً شاملاً للـDB وStorage تلقائياً.

**ما أنجزته:** مدقق حزمة مستقل للملفات والأحجام وSHA-256، يطابق كل ملف Storage بجرد bucket/object؛ يرفض ملفاً ناقصاً أو معدلاً أو مكرراً والمسارات الخارجة والروابط الرمزية. حارس هدف يرفض مشروع الاختبار الحالي والإنتاج حتى لو أضيفا لقائمة السماح بالخطأ. اختبارات إيجابية وسلبية بملفات اصطناعية. هذا تدقيق سلامة حزمة وليس pg_restore، ولا يثبت صحة SQL أو اتساق اللقطة أو أصالة manifest إذا تلاعب مهاجم به وبالنسخة معاً.

**ما سأقوم به بعد الوصول:** تثبيت أداة التصدير الملائمة وتثبيت نسختها، ثم تصدير المصدر للقراءة فقط (schema/data/roles وفق دليل المزوّد) وجرد Auth والإضافات وRLS وfinance_private والمهاجرات. تنزيل بايتات Storage بخدمة مخوّلة، مع تعداد كامل وصفحات الجرد وبصمات الملفات. تسجيل بداية/نهاية التصدير وإعادة فحص التغييرات أثناء النسخ؛ لا إعلان اتساق DB/Storage دون معالجة الفرق. حفظ النسخة مشفرة خارج المصدر، وحفظ بصمتها في موضع منفصل موثوق. لا نحفظ نسخة Auth أو الأسرار في Git أو تقرير عام.

**تسلسل الاستعادة الجاهز:** هدف فارغ مستقل، البريد/webhooks والمدفوعات الخارجية مغلقة؛ تحقق من معرفه قبل الكتابة؛ استعادة DB وفق نسخ PostgreSQL والإضافات المتوافقة؛ استعادة Storage عبر الآلية المدعومة؛ مطابقة الجرد والبصمات وعدد الصفوف وRLS والمنح والدوال؛ اختبار وصول مخوّل ومرفوض بحسابات اصطناعية؛ مراجعة أوامر المحاسبة والإيصالات دون حركة جديدة على الطلبات المحمية. لا تحويل التطبيق أو DNS إلى الهدف. قياس الزمن الفعلي والفجوة الزمنية، ثم تقرير الفشل/النجاح قبل تنظيف الهدف.

**قرار المالك:** حدد مشروعاً فارغاً موجوداً يجوز استخدامه كهدف مؤقت (رابط/اسم، دون أسرار)، أو وافق على طلب عرض كلفة مشروع منفصل في منظمتك الحالية. سأجهّز الهدف بعد تحديده والوصول المخوّل؛ لا يلزم أن تنفّذ التصدير أو الاستعادة بنفسك. لا نعتمد إنشاء مدفوع مسبقاً.

**الوصول الآمن عند الحاجة:** من مشروع الاختبار افتح Connect لاختيار الاتصال المدعوم، ومن الهدف افتح Connect أيضاً. بيانات اتصال DB تحفظ عبر إدخال آمن عند توفيره أو داخل مدير أسرار بيئة التنفيذ، وليس الرسائل أو مستودع Git. لا تعِد تعيين كلمة قاعدة البيانات الحالية من أجل الفحص. إذا لم تتوفر كلمة الاتصال الحالية، نستخدم مسار تصدير مدعوم آخر بعد التحقق؛ لا نستخرج كلمة سر عبر المتصفح. صلاحية Storage للقراءة بالمصدر والكتابة بالهدف تحفظ في الموضع الآمن نفسه. هذه الحزمة لا تتضمن منفّذ تصدير حي لأن نوع الهدف والوصول لم يُحددا بعد.

**الكلفة:** مساحة النسخ/نقل الملفات/حوسبة الهدف قد تُحاسب؛ القيمة غير معروفة دون حجم وهدف وتسعير المنظمة. لا Pro أو PITR أو تخزين مدفوع مفعّل. RPO وRTO غير مقاسين؛ المقترح القديم 24 ساعة/8 ساعات ليس ضماناً.

## 3. وصول تنبيهات الحوادث

**الموجود:** سجلات وبعض مسارات استقبال أحداث التطبيق، مع حدود أدلة سابقة. لا مستلم حادث معيّن، ولا إثبات إرسال واستلام خارجي. مفاتيح رسائل تغيير الحساب في Supabase معطلة، وهذه ليست بديلاً عن تنبيه حوادث مركزي.

**ما أنجزته:** نموذج حدث اصطناعي بقائمة حقول مسموحة فقط؛ يحذف الرسائل والروابط والرموز والموقع وأي حقول إضافية. أنواع ثابتة: كثرة فشل الدخول، رفض صلاحية، تعطل خدمة، تجاوز عتبة تكلفة. تجربة نقل محلية بقيم استجابة مصطنعة: ثلاث محاولات كحد أقصى لأخطاء الخادم، توقف عند429 أو رفض دائم، معرّف حدث ثابت. لا قناة إرسال فعلية. نجاح HTTP لا يسجل تلقائياً استلام إنسان. لا ادعاء بمنع كل التكرارات أو بضمان تسليم exactly-once.

**التجهيز التالي الذي أتولاه:** ربط مصدر الحدث الحقيقي بقناة الاختبار المعتمدة، حفظ الحدث دون أسرار، اختبار فشل النقل والتصعيد، ثم حدث واحد يحمل TEST وتسجيل وقت توليده واستلامه وإقرار المستلم. قياس التأخير. اختيار عتبات فعّالة يحتاج خط أساس استخدام؛ لا نطبّق أرقاماً اعتباطية أو نخلط تنبيه المصروف بسقف يوقف الإنفاق.

**قرار المالك:** اسم المسؤول وقناة واحدة يملكها، والإذن بإرسال تنبيه اختبار واحد إليها. مثال قرار: «أنا المستلم، القناة البريد المعتمد للاختبار، أوافق على تنبيه اصطناعي واحد». اختيار القناة لا يفوض تفعيل خدمة مدفوعة. بعد اختيارها سأجهّز الربط؛ أي سر يحفظ في Secrets للبيئة المستضيفة، لا في الرسائل أو الواجهة. إذا كانت القناة غير متاحة بالأدوات، سأحدد شاشة الربط المطلوبة حسب القناة المختارة بدلاً من اختراع مسار الآن.

**الكلفة/الوصول:** الاختبار المحلي بلا خدمة جديدة؛ كلفة القناة والسجلات والاحتفاظ تعتمد على الاختيار. المستلم ومناوبة الاستجابة غير معتمدين بعد. نقل السجلات إلى مكان منفصل وصلاحياته واحتفاظه ما زالت تحتاج إثباتاً.

## 4. حدود المحاولات وشبكة منفصلة

**الموجود:** /auth/v1/token يجمع دخول كلمة السر والتجديد ضمن حد IP الحالي150/5دقائق، وليس30 لكل طرق الدخول. يوجد burst وسلوك token bucket، فلا يصح انتظار رفض الطلب151 ببساطة. الحصة مشتركة خلف NAT ولا تمنع إساءة موزعة أو تكلفة كل الخدمات. لا اختبار استنفاد على IP الجلسات المحمية.

**ما أنجزته:** منفّذ إعادة تشغيل محلي لاستجابات اختبارية، سقف8 أحداث افتراضياً/16حداً أعلى، يتوقف فور429/timeout/5xx دون محاولات خلفية. حالة إيجابية تواصل المرور الطبيعي ضمن الميزانية. لا اتصالات شبكة؛ نجاحه يثبت انضباط أداة التحضير فقط.

**الاختبار الحي الذي أتولاه بعد العزل:** مشروع Auth مؤقت لا يضم الحسابات الخمسة، وخروج شبكة مخصص ثابت مثبت في سجل المزوّد، مع عدم تزوير forwarded IP وعدم تبديل الشبكة للهروب من الحظر. حسابان اصطناعيان A/B؛ طلب طبيعي لكل منهما؛ على الهدف المؤقت فقط حد صغير معتمد وقابل للإرجاع إن سمح المزوّد، حتى تكفي ميزانية≤16 بدلاً من مئات المحاولات؛ توقف أول429. اختبار أثر الحصة المشتركة للحساب B مرحلة منفصلة بطلب واحد معتمد ضمن تجربة العزل، لا حلقة أثناء الحظر. ثم انتظار Retry-After إن وجد/فترة الاستعادة الموثقة وطلب واحد. حفظ الأوقات والحالات ومعرفات الطلبات دون الرموز. إذا لم يظهر429 ضمن الميزانية، النتيجة غير حاسمة ونقف؛ لا نرفعها آلياً. لا نولد بريد استعادة بالجملة.

**قرار المالك:** يمكن استخدام المشروع المؤقت نفسه المقترح للاستعادة، لكن بخطة فصل زمني وحسابات اصطناعية؛ حدد توفر بيئة تنفيذ/جهاز اختبار بخروج شبكة لا تستخدمه جلسات TALABOT الحالية. سأجهّز التشغيل المحدود بعد إتاحة الاتصال. لا يكفي تبويب خفي أو VPN يتغير تلقائياً. توفير شبكة جديدة مدفوعة يحتاج عرضاً واعتماداً منفصلين.

**حدود النتيجة:** نجاح الحد الصغير ليس قياساً مباشراً للحصة150 المنشورة. اختبار400/429 وحده لا يثبت CAPTCHA أو كشف الطلبات الوهمية أو سقف كلفة الخرائط/التخزين. إبقاء حدود الشبكة الحالية دون تعديل يحافظ على الجلسات.
