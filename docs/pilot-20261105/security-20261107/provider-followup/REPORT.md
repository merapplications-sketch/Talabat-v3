# TALABOT — متابعة أمنية من eca1d48
الإصدار المنشور بقي .31، المصدر ea65f5289f3d19ccc5d3dbb65b59650e23e01370. هذه دفعة أدلة بلا تغيير كود أو إعدادات أو حسابات.

## المثبت
Auth Hooks: public.pilot_session_token_hook مفعّل فعلياً كـCustom Access Token hook. تعريفه الحالي يرفض الحساب المحظور أو session_id المسجل في revoked_sessions. يُربط هذا بأدلة session-revocation/lifecycle-http-14.json السابقة؛ التفعيل وحده لا يغلق V7.4.2 ولا حذف الحساب/Realtime/الروابط القديمة.
SMTP مخصص غير مفعّل. قوالب البريد الافتراضية ظاهرة، ومفاتيح تنبيهات تغيير كلمة السر والبريد وطرق الدخول وMFA غير مفعّلة. لا دليل وصول بريد أو تنبيه.
لوحة Backups تؤكد أن الخطة المجانية لا تشمل نسخ المشروع؛ لا نسخة مجدولة متاحة لاختبار استعادتها. لم تُنفذ استعادة على المشروع الحالي.

## تصحيح تفسير حدود المحاولات
عنوان لوحة المزوّد لا يكفي لتعيين المسار: وفق توثيق Supabase، password sign-in وrefresh يستخدمان /auth/v1/token، وحده الحالي150 طلباً/5دقائق/IP، مع burst منفصل حسب المزوّد. حد30/5دقائق يتعلق بمسارات التسجيل والاستعادة وإعادة الإرسال والتحقق المبيّنة بالتوثيق؛ لا يصح إعلان أن كل دخول بكلمة سر محدود بـ30.
الحدود مشتركة لكل IP: مستخدمون خلف NAT يتنافسون على الحصة، بينما تعدد IP قد يوزع الإساءة. ليست حماية مستقلة لكل حساب ولا سقف تكلفة شامل.
الاختبار الحي لاستنفاد الحصة لم ينفذ: IP المتصفح الحالي مشترك مع الجلسات المحمية، فلا أُحدث حظراً عليها. يلزم هدف Auth مستقل قابل للتخلص وخروج شبكة مخصص، لا مجرد حساب جديد بالمشروع نفسه.
خطة الاختبار المحدود: حسابان اصطناعيان خلف IP الاختبار، قياس قبول طبيعي لكل منهما، اقتراب تدريجي من الحد مع سقف ثابت وتوقف عند أول429، محاولة واحدة للحساب الثاني لقياس الأثر المشترك، ثم انتظار نافذة الاستعادة ومحاولة واحدة. لا رسائل بريد متكررة ولا كلمات سر حقيقية ولا تغيير عناوين لتجاوز الحظر. هذا اختبار مُحضّر وليس نتيجة نجاح.

## غياب الحماية والبدائل — دون تطبيق سياسة جديدة
كلمات السر المسرّبة: قد تُقبل كلمة معروفة بالتسريب؛ حدودIP لا تمنع إعادة استخدام كلمة مسرّبة صحيحة. MFA الإداري يقلل الخطر ضمن الحسابات المشمولة فقط. بديل محتمل: قائمة حظر خادمية محلية/خدمة تحقق خصوصية، لكن يلزم تغطية التسجيل والتغيير والاستعادة المباشرة؛ فحص الواجهة وحده قابل للتجاوز. لا تفعيل خدمة أو إرسال كلمة سر لطرف خارجي دون اعتماد.
مدة الجلسة والخمول: JWT ساعة لا يعني أن الجلسة تنتهي بعد ساعة؛ refresh قد يبقيها مستمرة. الحظر وسجل الإلغاء وحارس الخادم حماية حالية جزئية. بديل خادمي محتمل: عمر جلسة/آخر نشاط في قاعدة البيانات وحارس لكل مسار، مع تغطية Auth/Realtime/Storage؛ المؤقت في الواجهة وحده غير كافٍ. سيغيّر سياسة الدخول ويحتاج اعتماداً واختباراً قبل تطبيقه.
CAPTCHA غير مفعّل؛ لا أضيفه للزبائن ضمن هذا التفويض.

## التدخل المطلوب بدقة
1. البريد: تحديد صندوق بريد اختبار يسيطر عليه المالك والإذن باستخدامه لحساب اصطناعي منفصل. البريد الافتراضي يقبل عناوين فريق المشروع فقط وفق الوثائق؛ لا تمنح عضوية تنظيمية إضافية لمجرد الاختبار. البديل: مشروع الاختبار > Authentication > Emails > SMTP Settings، إدخال إعدادات مزوّد بريد اختبار معتمد بأمان وحفظها، بعد اعتماد أي تكلفة. لا ترسل كلمة SMTP بالمحادثة.
2. الاستعادة: توفير تصدير DB فعلي ونسخة مستقلة من ملفات Storage وهدف Postgres منفصل قابل للتخلص واتصال محفوظ بأمان. قاعدة البيانات وحدها لا تحتوي بايتات الصور. لا اعتماد RPO/RTO قبل تجربة فعلية.
3. التنبيهات: تحديد المستلم والقناة والإذن بإرسال حدث اصطناعي؛ ظهور السجل لا يثبت وصول التنبيه.
4. اختبار حدودIP: هدف Auth وخروج شبكة مستقلان عن الجلسات الخمس. لا خطة مدفوعة أو ضغط على الخدمات دون اعتماد.
