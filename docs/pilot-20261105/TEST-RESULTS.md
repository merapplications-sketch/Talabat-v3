# النتائج وحدود الإثبات

بيئة مجانية مؤقتة على GitHub Actions Ubuntu24.04: PostgreSQL17.6 أصلي متعدد الاتصالات، GoTrue2.197.0 حقيقي وPostgREST14.18 حقيقي، جميع المنافذ loopback، بيانات وأدوار اصطناعية، ثم حذف الحاويات والبيانات. المصدر يعيد كتالوج SQL المحفوظ ولا يجري SQL حياً. A/R1 ثابتتان؛ الرقع الجديدة proposed فقط. صور الحاويات وبصماتها بكل attempt. التسجيل الحقيقي للبريد مع autoconfirm مختبري فقط، وليس اختبار SMTP. سر JWT وكلمات المرور وجلسات الدخول والنسخة الاحتياطية لا تُصدر ولا تحفظ على GitHub.

الربط المحلي يشغّل صفحات المرشح الفعلية وSupabaseJS2.117.2 عبر bridge لمسارات Auth/REST. لا Kong ولا Realtime WebSocket ولا Storage فعلي. قبول هذا الربط المحلي لا يغلق إعدادات Supabase المستضافة.

## الإضافات التي نُفذت

[sجل القبول المجمع](integration-acceptance-ledger.json) يربط كل نجاح بمصدره ومحاولته، ولا يحسب الاختبار المتجاوز كتجربة جديدة. [محاولة5](attempt-5.json) تثبت إصلاح التعويض وأزرار السائق، و[محاولة6](attempt-6.json) تثبت توسيع عزل الأدوار. فحوص53 وحالات التزامن10 المغلقة لم تُعد. إعادة أقصى حمل بعد تغيير place_order واستعادة الدوال بعد تغيير SQL تحقق متأثر مقصود، لا إعادة شاملة.

- Auth signup/password/refresh، رفض التزوير، RLS العناوين، بوابة pending للسائق، أسعار/توافر/رفض ذري، مفاتيح الطلب والتعافي، الإلغاء/المحفظة، سجل الخطأ الخاص.
- رحلة REST كاملة بمحاسب مفوض اصطناعي: قبول مطعم وتجهيز وإسناد والتقاط وموقع وتسليم65 TJS وعمولة10 ومستحق15، ثم تسوية وإيصال وهوية/توقيت خادم. إسقاط جسم الرد بعد commit ثم قراءة الحالة بنفس UUID يعيد الإيصال دون execute إضافي.
- Chromium Linux على صفحات فعلية:8 فحوص دخول/دفع/offline/فقد رد/مفتاح/إغلاق وإعادةفتح/استرجاع/محركPDF، و7 فحوص أزرار السائق والتأكيد. [دليل المتصفح](evidence/result-browser.json)، [أزرار السائق](evidence/final-result-driver-actions.json).
- عزل REST إضافي13دليلاً: عميل آخر/مطعم آخر/سائق بلاعرض لا يرون تفاصيل الطلب، لا عناوين عميل أو أعمدة مالك/عمولة، لا رفع دور أو كتابة طلب مباشرة، مدير دون finance لا يقبض.
- سباق التعويض: قبل الإصلاح80على طلب65، وبعد قفل التذكرة/الطلب40مرة واحدة ورفض refund_too_high؛ فشل التخزين أعاد التذكرة والرصيد والتدقيق معاً.
- سباق سائق واحد/طلبين: محاولة6 غير حاسمة بسبب snapshot مراقب المعاملة؛ محاولة7 بمراقب autocommit أثبتت قبول الطلبين. [محاولة8](attempt-8.json) بعد قفل ملف السائق: طلب واحد قُبل والثاني busy، وبقي سائقان/طلب واحد بفائز واحد؛ استعادة الدالة اجتازت، لا علاقة لهذا بإغلاق التزامن المالي السابق.
- watchdog:4فحوص محلية لانتقال عطل/عدم تكرار التنبيه/تعافٍ. الناتج outbox فقط؛ لا جدولة أو توصيل تنبيه لمناوب فعلي.

## الحمل الجديد: الطلب والتتبع

[محاولة3](attempt-3.json) شغلت85رحلة على بيانات تاريخية10000طلب؛ كل رحلة15استدعاء تشمل quote/place/prep/status/assignment/pickup/GPS/قراءةالتتبع/deliver. إسناد الحمل إداري لتثبيت القياس، وسباق قبول العرض اختبار وظيفي مستقل. تحديثات الموقع3متباعدة3.05ثوانٍ، وليس تدفق GPS أسرع من حد الخادم.

في الجولة الأخيرة أكثر زمن تجميعي: place_order50مرة1790.68msبمتوسط35.814ms، ثم انتقال الحالة150مرة1414.07msبمتوسط9.427ms. RESTpool20، PostgreSQLmaxconnections200. لا اختناق مثبت أو قياس CPU/IO كافٍ لتحديد التشبع؛ لا نضيف فهارس تخمينية. خطة Supabase الحقيقية وحصص البريد/التخزين/Realtime غير مقاسة؛ المجاني ليس ضمان سعة أو uptime.

## النسخ والاستعادة

pg_dump/pg_restore أصليان إلى قاعدة مستقلة، مقارنة محتوى13جدولاً بما فيها auth.users والجداول المالية وبصمات141تعريف دالة. محاولة4 تحتوي أوامر وإيصالاً فعليين وبيانات الحمل؛ محاولة5 تراجع تغير دالة التعويض، ولو كانت جداول الإيصال خالية في تلك الجولة. أحدث استعادة تخص تعديل driver_accept فقط. لا بيانات أو نسخ حقيقية، ولا استعادة ملفات Storage. لا ادعاء RPO/RTO للمشروع الحي.

## المفتوح بوضوح

Safari على iPhone، Android فعلي، GPS/الخلفية/منع الأذونات، حوارالطباعة والطابعة، SMTP/reset الحقيقي، Realtime/Storage وقواعدهما، إعدادات Auth/PostgREST المستضافة ومطابقتها للكتالوج، نسخ حقيقية وتنبيه يصل إلى مناوب. الفريق مسؤول عنها؛ لا مطالبة للمالك بجمع تسجيلات تقنية. عدم توفر الجهاز ليس عيب تطبيق، وعدم وجود Push بالمصدر نقص مثبت لا اختباراً فاشلاً.
