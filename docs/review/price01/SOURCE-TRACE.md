## The contract boundary, precisely

The current request cannot distinguish two customer approvals whose only difference is the displayed item price/total: identities, options, quantities, tip, fee and selected wallet amount can all be identical. A server-only re-read cannot infer the missing approval. Conversely, attaching today's price to an already frozen request would not prove what the customer approved and would change its HMAC-covered input.

`docs/review/continuation103/CONTRACT.md` retains old-client creation through the same bigint wrapper and says all unknown extra properties are fingerprinted. `tests/native103/schema.sql:39–70` supplies the unchanged canonicalizer/HMAC/verifier; `tests/native104/schema.sql:2–4` supplies the fixed float-context payload constructor. No cryptographic rewrite is necessary. Requiring new price evidence at creation changes old-client compatibility, hence the explicit contract proposal before implementation.
