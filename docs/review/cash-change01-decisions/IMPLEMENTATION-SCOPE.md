# أصغر نطاق مرشح بعد القرارات — غير منفذ وغير مفوض بهذه الوثيقة

هذه إضافة إلى العقد المقبول للتحضير، لا إعادة كتابة له. جميع الأسماء أدناه **مقترحات**، لا endpoints أو جداول موجودة.

## فصل التنفيذ عن CC-E01

| الوحدة | هل تعتمد على CC-E01؟ | ما يلزم قبل المرشح المحلي وما يبقى للتشغيل |
|---|---|---|
| CC-LOCAL-M1: تسليم + credit/event والتزام مقابل + استرجاع + سياسة سقف + حراس | لا | D01–04 المنطبقة وCC-AUTH المحلي. fixture اصطناعي معلوم الحدود؛ جرد تعريفات معاملة وتريغرات المصدر متاح للتحضير. CC-E02 والإثبات الحقيقي للكتّاب والعزل وCC-E03 والتعافي تبقى بوابات قبل تطبيق مستضاف |
| M2: قبض الإدارة **نقداً** لدين الفرق، بإيصال وبنود مستقلة | لا | تكليف محلي منفصل أو إضافة صريحة؛ إثبات المحاسب القائم وعقد سند القبض ومصالحة CC-E03. مدخل رقم أو COMMIT لا يثبت قبض أوراق نقدية؛ في المحلي الدليل اصطناعي معلن |
| M3: مقاصة الدين مع مستحق السائق | نعم، حاسماً | قبول المستحق، الصرف السابق، الحجوزات/التخصيصات، المتبقي المتسق، وwriter يستطيع حجز/استهلاك مرة واحدة مع الصرف. لا sum(payout) ولا delivery_due ولا إيصال CASH-01 يكفي. لا تنفيذ مالي على مستحقات فعلية أو إعلان قبول مقاصة باستخدام fixture بديل |
| تصحيح مالي تعويضي بعد COMMIT | لا يكفي CC-E01 وحده؛ وقد يلزم إذا استخدمت مقاصة | يتوقف على D04-B وعقد المسؤولية والتمويل وتفويض منفصل. في D04-A يتم التوثيق/الإحالة فقط |

لا يتوقف إعداد M1 أو M2 على دفتر مستحقات السائق؛ ولا يعني ذلك السماح بتشغيلهما الآن أو إغلاق CC-E02/E03. لا بناء محفظة سائق بديلة لتجاوز مانع المقاصة.

## API الأدنى المقترح لـM1

نطاق الملفات المقترح للتفويض المحلي، لا ملفات أُنشئت هنا:

| الملف/المسار | نطاق الدفعة المحتملة |
|---|---|
| `sql/proposed/cash_change01_candidate.sql` | نسخة مرشح جديدة، بعد مطابقة المصدر المحدد؛ لا تعديل ترقيعات SQL التاريخية |
| `sql/proposed/cash_change01_recovery_only.sql` | إيقاف الإنشاء الجديد مع بقاء الاسترجاع والمصالحة والقيود |
| `tests/cash-change01/` | fixture معلن، اختبارات PostgreSQL مستقلة، حالات فشل، وبناء نسخ عميل معزولة |
| نسخ معزولة من `driver.html` و`talabat-core.js` | عقد التسليم الجديد واللقطة المحفوظة وstatus وإظهار D/C/E؛ لا تعديل مسار إنشاء الطلب أو HMAC |
| نسخة معزولة من `customer.html` | عرض قيد الفرق المؤكد فقط؛ لا تعديل حساب رصيد المحفظة أو التسعير |
| نسخة معزولة من `admin.html` | إعداد السقف المقترح مع صلاحياته؛ معاينة وظيفية للموافقة، لا إعادة تصميم |
| نسخ معزولة من `assets/admin-finance/admin-finance.js` و`assets/finance-receipt/receipt.js` | M2 فقط عند تفويضه: سند قبض فرق مستقل، دون تغيير إيصالات CASH-01 القديمة |

تبقى ملفات التطبيقات التشغيلية نفسها بلا تعديل في المرشح المحلي الأول المقترح؛ الربط الفعلي والتفعيل والانتقال تفويض لاحق. إن اقتضى البناء غير ذلك، يُعرض الفرق قبل توسيع النطاق.

1. قراءة متطلبات التسليم/السقف: طلب مخول فقط، D/عملة/نسخة سياسة/حد السقف؛ ليست حجزاً أو نجاح تسليم. لا تُعرض هوية زبون أو أرصدة أكثر مما يلزم الدور.
2. `deliver_order_cash_change_v1`: request مستقل،order_id،C عشري نصي مضبوط،policy_version الموافق عليها،note/photo وفق العقد القائم. تؤخذ هوية السائق والزبون وT/W من الخادم. تحويل النص إلى numeric يحفظ القيمة تماماً ويتحقق من الدقة قبل الأثر؛ ليس تغييراً لـHMAC إنشاء الطلب.
3. تحقق هوية وتفويض حالي، ثم استرجاع الأمر المكتمل ومطابقة المدخلات **قبل** شروط الإنشاء والسقف الحالي. ثبات actor/request والحدث الواحد للطلب؛ مفتاح آخر لا ينشئ credit آخر. تغيير payload تعارض، لا overwrite.
4. تحقق pickedup/الإرجاع/الصورة والأهلية وD/C/نسخة السقف داخل المعاملة. compare-version مع قفل أو آلية مكافئة مثبتة تمنع تحديث السياسة بين الفحص والالتزام. يلتزم التسليم وحدثه وcredit والدين/الإيصال/command وكل الآثار الداخلية معاً، أو تتراجع كلها.
5. حالات الرد: committed/recovered،conflict،rejected_no_effect بعد إثبات التراجع،unresolved عند غياب الحسم. اختلاف السقف يعيد نسخة جديدة بأقل بيانات دون إعادة إرسال تلقائية. غياب command وحده ليس برهان عدم التنفيذ.
6. قراءة status مخولة لاسترجاع النتيجة الأصلية والمصالحة، لا تكشف طلب شخص آخر. العميل يحفظ لقطة المحاولة قبل الإرسال، ولا يغيّر المفتاح أو النقد عند timeout أو فقد ACK. إعادة المحاولة الجديدة بعد رفض مؤكد تحتاج حسم الأصل وموافقة لازمة؛ لا نجاح متفائل للمحفظة.

## Schema الأدنى المقترح

- `cash_change_private.delivery_commands`: المفتاح/الفاعل/الطلب/إصدار العقد/المدخلات المحدودة/النتيجة. منع تعديل أو حذف يفتح المفتاح من جديد.
- `cash_change_private.events`: حدث التسليم ذو order_id فريد،هوية الأطراف،D/C/E/عملة/نسخة سياسة/مرجع credit/الإيصال. **الحدث نفسه نشأة التزام السائق**؛ لا جدول محفظة سائق أو رصيد ثانٍ.
- `wallet_entries`: نوع cash_change وفهرس عدم التكرار لهذا النوع/الطلب. E>0 يتطلب قيداً مطابقاً للحدث في المبلغ والهوية والعملة والطلب، وبالعكس عندCOMMIT؛ FK أحادي لا يكفي. E=0 لا يولد قيداً صفرياً أو ديناً مصطنعاً.
- سجل سياسة بإصدار وربط مسار الإدارة القائم وتدقيقه. لا إعادة استخدام profiles.cash_limit ولا تغيير CASH-01.
- M2 وحده يضيف settlement/header/items/receipt/commands منفصلة لقبض الفرق؛ M3 وتخصيص المستحق غير موجودين في تفويض M1. لا placeholder مقاصة مالية يقبل رقماً مرسلاً من العميل بدلاً من CC-E01.
- سياسات دورة الحياة تحمي UPDATE/DELETE/TRUNCATE وFK cascade/SET NULL بحسب علاقة كل سجل. لا ننسب حماية DELETE إلى تريغر BEFORE UPDATE فقط. تفاصيل الحراس والمنح نفسها تحتاج اعتماد ومراجعة، وليست RLS منفذة.

## Guards والتوافق

الحارس المستقبلي يغطي deliver_order وset_order_status والكتّاب المباشرين وغير المباشرين المعنيين، فلا يكفي wrapper سائق. لا يُغيَّر writer تاريخي الآن ولا تُفعّل الحواجز على مستضاف. يجب إثبات كل مسار قائم قبل إيقاف توافقه؛ العميل القديم يسترجع ما يحق له من نتائج قديمة، ولا يستطيع إنشاء حدث جديد خارج العقد بعد انتقال معتمد.

لا نسخ عشوائي لترتيب أقفال106: التصميم يراجع order/profile/driver/command/policy وStorage والولاء والإرجاع والتسوية معاً. لا استدعاء settle_cash داخل تسليم يحتفظ بقفلorder ثم يطلب قفلdriver. يبقى CASH-01 منفصلاً. إن لزم تغيير ترتيب قفل أو عقد محمي خارج التوسعة المعتمدة، يعرض التعارض قبل التعديل. RC/RR/Serializable تُثبت أو ترفض قبل الأثر؛ advisory lock ليس تحديثاً للـMVCC.

## Rollback والتعافي

المرشح المقترح يضيف ملفات جديدة، دون إعادة كتابةSQL التاريخي. الرجوع يوقف الكتابة الجديدة إذا لم يعد الزوج المالي مضموناً، ويحافظ على status/replay والأحداث والمفاتيح والقيود والإيصالات والسياسة التاريخية؛ لا DROP أو TTL أو DELETE يعيد الفتح، ولا عودة لكاتب قديم يتجاوز الحارس. إعادة الترقية لا تضاعف الأثر. لا backfill لطلب مكتمل بلا حدث.

استعادة DB لا تثبت وحدها قبض/رد النقد خارجها. يلزم ربط نقطة النسخة وإيصالات ما بعدها وStorage والمفاتيح والأوامر غير المحسومة، ثم مصالحة قبل إعادة فتح الكتابة. لا RPO/RTO أو سياسة احتفاظ جديدة هنا. إلغاء/رد الطلب لا يعكس E تلقائياً لأنه نقد زائد للزبون، ولا يغير مستحقاً تاريخياً.

## طلب الأدلة المحدد

- **CC-E01:** حامل دفتر الاستحقاق والصرف/المالية يقدم اسم المصدر وschema/API ومرجع قبول الاستحقاق وتاريخات الصرف والحجز والمقاصة والمتبقي عند نقطة اتساق، مع الكاتب وآلية منع الصرف المزدوج ودليل تخصيص. عينة منقحة خاصة تكفي للتحضير؛ لا أسرار أو أسماء أشخاص فيGitHub. إن كان المصدر خارج DB، يلزم عقد حجز/التزام/إلغاء ومصالحة؛ لا distributed atomicity مفترضة.
- **CC-E02:** مسؤول النشر/DB وكل Worker أوJob يربط active version/source digest/بيئة بالتعريفات والكتّاب والحدود الفعلية للمعاملة. سجلات نشر قديمة ليست حالة حالية. لا إعادة تشخيص عام أو استعلام جديد ضمن هذه الحزمة.
- **CC-E03:** المالية تقدم سند قبض/رد ومرجع مصالحة؛ حافظ النسخ/Storage/المفاتيح يقدم backup ID/version/وقت/نطاق وحالة إتاحة واستعادة متسقة. نجاح run اصطناعي لا يغلقها.
