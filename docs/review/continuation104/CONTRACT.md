## Atomic browser state
IndexedDB readwrite transactions with strict durability store an account record. Each attempt has a cryptographic UUID, stable client key, increasing state version, frozen RPC payload and a SHA256 cart revision token. The account has a single active attempt. Check+claim and conditional completion happen in one IndexedDB transaction; RPC is outside it. BroadcastChannel is not a lock and is not required. Unsupported/failing storage fails closed before creation.
A response may mutate only its captured attempt UUID/version. It cannot remove another active key. A closed/succeeded key is retained as metadata, preventing accidental resurrection. Reload/crash preserves pending state; a new tab uses status lookup. Explicit retry reads first, then may send only the original payload/key when still not visible. Network and saved-order re-read waits are bounded; timeout is unresolved, not cancellation. There is no automatic new key or time-based abandonment.
The fence is account-scoped within one browser origin/profile. Separate devices/profiles have no shared IndexedDB; cross-device global intent coordination is NOT established. Server idempotency/fence protects the same key, not two independently generated keys. Any requirement to enforce one unresolved intent across all devices needs a separately reviewed server intent/session protocol. Origin-data deletion similarly requires server reconciliation; no browser-only mechanism can preserve deleted data.

## Cart and rejected-attempt lifecycle
The generated customer function captures a live cart/context token separately from submitted payload and compares it on completion. Later cart changes are preserved in full; it does not subtract potentially unrelated quantities or restore an older cart. Historical/status-only recovery preserves cart. Shared legacy cart mirror changes detected while watched set a foreign-change flag; the old tab stops writing that mirror and asks for reload. The existing synchronous cart mirror is not being declared a complete atomic multi-device cart service.
A rejected result alone never ends an attempt. User-confirmed endRejected re-reads authenticated status104, verifies terminal closure UUID/version/no_effects, then atomically marks that specific attempt ended and releases only its own pointer. It erases frozen sensitive payload on this transition. Customer retains editable cart, clears old key, and creates a fresh key only on the next explicit order confirmation. Unknown attempts have no unsafe cancel/delete path; they require continued reconciliation or authorized support escalation.
Generated overlay uses existing RU/EN alerts/confirmations; no CSS/layout changes or deployed preview. Actual Safari acceptance and any future visual redesign remain separate.

Browser storage is origin-protected plaintext, not a secure enclave or at-rest encryption guarantee. Store only the exact payload needed for retry; cart revision is a digest, not a second raw cart/recipient copy. Do not log payloads, secrets or database dumps. Support escalation should exchange authenticated attempt references/status, not passwords/MFA or raw recipient details in chat. Local metadata expiration must not let the old key become a fresh operation. Any retention deletion policy needs independent owner approval and a reconciliation design before implementation.
