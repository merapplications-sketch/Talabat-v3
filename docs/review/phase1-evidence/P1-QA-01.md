## 1 — group_get ليس مسار قراءة خالصاً
**المدخل:** TLB.groupGet(id) يتحقق من صيغة UUID ثم يستدعي RPC group_get مع p_id؛ [talabat-core.js:1167](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/talabat-core.js#L1167). تحقق الصيغة في العميل ليس تفويضاً خادمياً.
**التوقيع التاريخي:** group_get(p_id uuid) returns jsonb؛ PL/pgSQL SECURITY DEFINER، search_path=public؛ [sql/schema_patch33.sql:93](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/sql/schema_patch33.sql#L93).
**التفويض في هذا النص:** يشترط auth.uid() غير NULL. لا يظهر شرط ملكية المضيف داخل group_get؛ التعليق التاريخي يسمح للمسجل صاحب الرابط برؤية المجموعة. EXECUTE ممنوح لـ authenticated ومسحوب من public/anon عند 142–143؛ المنح المباشرة على group_orders/group_items مسحوبة من anon/authenticated عند 67. هذا وصف المصدر وليس قبولاً لصلاحيات الهدف الحالية.
**الأثر:** UPDATE group_orders SET status='cancelled' WHERE id=p_id AND status='open' AND expires_at<now()، ثم RETURN group_json(p_id). لا إدراجطلب أو خصم مباشر ظاهر في جسم group_get. لا نستبعد آثار تريغرات الهدف غير المقروءة.
**الاعتماديات:** auth.uid،وقت now،group_orders(id/status/expires_at)،group_json(uuid). تعريف group_json عند 70–78 يقرأ group_orders و profiles لاسم المضيف و group_items لتجميع العناصر؛ تنفيذه المباشر مسحوب من public/anon/authenticated.
**المعاملة و الأقفال:** UPDATE و الاسترجاع ضمن استدعاءالدالة نفسه في معاملة المستدعي؛ لا COMMIT مستقل أوحد خارجي ظاهر. UPDATE يأخذ أقفال الكتابة المعتادة، ولا يوجد advisory lock صريح أو FOR UPDATE منفصل في هذا الجسم. لا يمكن استنتاج ترتيب الأقفال الكلي دون التريغرات والكتّاب الآخرين. فشل غير معالج لاحقاً يلغي أثر المعاملة بنيوياً؛ لم يُختبر ذلك هنا.
**ACK/التصريف:** إذا التزم UPDATE ثم فُقد الرد فقد تكون المجموعة cancelled بالفعل؛ لا يُعامل الاستدعاء كقراءة آمنة لمجرداسمه. إعادةاستدعائه لا تطابق شرط open للمجموعة الملغاة، لكن ذلك ليس برهاناً شاملاً على idempotency كل تريغر أوكاتب. إدراجه إلزامي فيجردالتصريف والتزامن مع group_set و place_order؛ لا تصريح بإعادةإرسال تلقائي.
**الناقص:** تعريف النشر،كل تريغرمتعدٍ،دوروعزل RPC الفعلي،وترتيبأقفالالكتّاب. يوفرها DB ومسؤول API/النشر؛ يقبلها QA مستقل. المسار المستضاف BLOCKED.

## 2 — check_promo يكتب promo_guess
**المدخل:** TLB.checkPromo(storeN,cart,code) يجهز p_code/p_store/p_items ثم sb.rpc('check_promo',...)؛ [talabat-core.js:1257](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/talabat-core.js#L1257).
**التوقيع التاريخي:** check_promo(p_code text,p_store uuid,p_items jsonb) returns jsonb؛ SECURITY DEFINER و search_path=public؛ [sql/schema_patch30.sql:44](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/sql/schema_patch30.sql#L44).
**الجداول و الكتابة:** promo_guess(id identity,user_id uuid,at timestamptz DEFAULT now(),bad boolean)، فهرس(user_id,at DESC)،RLS مفعّل والمنح المباشرة مسحوبة من public/anon/authenticated عند 15–23.
الدالة تقرأعدادات المستخدم ثم INSERT لمحاولة، ثم DELETE لصفوف المستخدم الأقدم من يوم؛ [sql/schema_patch30.sql:74](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/sql/schema_patch30.sql#L74). سجل bad ليس مرادفاً لفشل HTTP أوفشلإنشاءطلب.
**تسلسل التنفيذ التاريخي:**
1. رفض auth.uid NULL؛ قفل pg_advisory_xact_lock(hashtext('promo_guess:'||uid)).
2. عد bad وكلالمحاولات خلال 10 دقائق؛ يرفع too_many عند bad>=10 أو all>=60. هذه ثوابت النص التاريخي وليست اعتمادسياسةإنتاج جديدة.
3. إنوجد happy_hour_pct وكانتنتيجته موجبة يرجع promo_offer مبكراً دون INSERT/DELETE في هذاالجسم.
4. يستدعي check_promo_base داخلكتلة EXCEPTION. خطأ too_many يعادرفعه؛ غيره يتحولإلى JSON خطأ. بعدذلك تُحسب bad وفق ok وقائمةالأخطاءالمستثناة،وتُدرج المحاولة ثمينفذ التنظيف.
5. EXECUTE على check_promo(text,uuid,jsonb) ممنوح authenticated ومسحوب public/anon عند 81–82.
**الاعتماديات غير المحسومة:** patch30 يعيدتسمية check_promo الموجود إلى check_promo_base فقط عند غيابه،ويبحثعنالتواقيع في pg_proc ويسحبمنحتنفيذ المساعد. لذلك محتوى المساعد يعتمدعلىتاريخالتثبيت؛ لا يجوز اختيار patch سابقاعتباطياً باعتباره النسخة الفعلية. وجودمصدرمساعدغيرمحدد فيهذا التصحيح لايثبتغياب المساعدمن الهدف. happy_hour_pct استدعاءديناميكي مشروطبوجوده؛ آثاره واعتماديات base تحتاجتعريفاتمثبتة.
**المعاملة:** قفل advisory معاملاتي؛INSERT و DELETE ضمنمعاملة المستدعي ولا COMMIT مستقل. استثناء base الملتقط يتراجععنكتلته الفرعية،ثمقديحفظالغلاف سجل المحاولة إذاالتزمت المعاملة الخارجية. تعليقالملف عنبقاءالسجل لا يعني أنه ينجو من ROLLBACK خارجي أوفشللاحق. خطأ التنظيف غيرالمعالج يرجعإدراج المحاولة أيضاً؛ لم ينفذ اختبار.
**الموارد/ACK:** كل إعادة فحص قد تضيف صفاً جديداً وتستهلكالحصة؛ لامعرفعملية dedup ظاهرللفحص. فقد ACK لايثبتأنالسجللم يُكتب. التنظيفمقيدب المستخدم وبالوصولإلىنهاية المسار؛ ليس TTL عاماً أوسقفاًعالمياً أوحمايةمعدللكلإنشاءطلب. الصفوفالمبكرة too_many/HappyHour لاتنفذ التنظيف هنا.
**الناقص:** تعريف base الحقيقي وتواقيعه،النسخة المنشورة وآثارمساعداته وتريغرات promo_guess والعزل/الأقفال/الموارد. يوفرها DB وحافظتاريخ الترحيل ومسؤول API؛ يقبلها QA أمنيومالي مستقل. BLOCKED مستضافاً؛ لايقترح التصحيح تغييرالحدود.

## 3 — rate_order ومكافأة التقييم المحتملة
**السلسلة المصدرية المثبتة:** sendRate في[customer.html:1910](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/customer.html#L1910) يستدعي TLB.rateOrder عند 1913؛ النواةعند[talabat-core.js:956](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/talabat-core.js#L956) تتحققمننجوم 1..5 ومنوجودتقييمثم RPC rate_order مع p_order/p_store/p_driver/p_comment.
هذا يثبتأسماءمعاملات العميل فقط؛ توقيع SQL ونوعالإرجاع وتعريف rate_order الفعلي وتفويضه وكونه INSERT أو UPDATE غير مثبتةمنالمواضع المحددة. لا نملأهذه الحلقة بالتخمين.
**الأثر التاريخي المثبت بصورة مستقلة:** [sql/schema_patch32.sql:99](https://github.com/merapplications-sketch/Talabat-v3/blob/0d25e451fa99d5d60f834257ccf70a8f5d2de52e/sql/schema_patch32.sql#L99) يوسع kind لقبول reward في loyalty_lots/loyalty_ledger ويضيف unique index loyalty_one_reward_per_order على loyalty_lots(order_id) WHERE kind='reward'.
trg_rating_reward() returns trigger عند 106: SECURITY DEFINER و search_path=public؛ يأخذ loyalty_setting('loyalty_rate_reward')::int. إذا النقاط>0 و new.customer_id و new.order_id غير NULL، يدرج lot بنوع reward ونقاط وانتهاءمحسوب من loyalty_expiry_days؛ ON CONFLICT(order_id) WHERE kind='reward' DO NOTHING RETURNING id؛ لا يدرج loyalty_ledger إلاعندعودة id للـ lot الجديد.
ربط trg_ratings_reward عند 118: AFTER INSERT ON ratings FOR EACH ROW. لذلك التريغريعملعلى INSERT حسب النص، وليس كل تعديل تقييم. المكافأةتتبع الإعداد؛ تعليق«+10» ليس دليلاًعلىقيمةتشغيل ثابتة.
**الجداول والاعتماديات:** ratings كمصدرحدث؛ loyalty_lots و loyalty_ledger ككتابة؛ new.customer_id/order_id؛loyalty_setting،قاعدةانتهاء النقاط،الفهرسالجزئي وقيود kind،وأيتريغراتعلىجداول الولاء. يجبإدراج ratings فيجردالاعتماديات خارجالجداولالخمس الأساسية.
**حدود المعاملة:** فيهذا التعريف،تريغر AFTER المتزامن و INSERT الـ lot والـ ledger ضمنمعاملة INSERT ratings المستدعية؛ لا COMMIT مستقل أونقلخارجيظاهر. فشل ledger غيرالمعالج يفشلالعبارةالتيشغلت التريغر ويرجعآثارها؛ يبقىسلوكأي EXCEPTION في rate_order وحدود المعاملة الخارجية غيرمعروف. لا إثباتاختباريجديد للذرية.
**منعالتكرار و المصالحة:** الفهرسوالـ ON CONFLICT يحميان lot reward لكل order_id فيهذاالمخطط،والـ ledger مشروطبإدراج lot جديد؛ هذااستنتاجنصي محدود،لا إثباتسلامةكلالكتّاب أو النشر. لا يدعم ادعاء once-per-user خارجشرط order_id. بعد ACK مفقود يلزمالتحققمن rating و lot و ledger المرتبطةب الطلب قبلأيإعادة؛ سلوك retry الفعلي وكتابة rate_order غير مثبتين. بعد restore يلزمحفظ الفهرس و الصفوف ومصالحةالالتزامات؛ لااختباراستعادةهنا.
عرضرسالةمكافأة في العميل أوإعادةتحميل النقاط ليس دليلاًعلىالتزام ledger. لا نفتحعيبواجهةجديداًبهذهالملاحظة.
**الناقص:** تعريف rate_order المنشور وتفويضه وحدمعاملته،ربط trigger الفعلي وحالتهو الفهرسو القيود وإعدادات الولاء وأيتريغراتمتعدية. DB ومسؤولنشر العميل يوفرانها؛ QA مالي وأمني مستقل يقبلها. السلسلةالكاملة إلىأثرمستضاف BLOCKED.
