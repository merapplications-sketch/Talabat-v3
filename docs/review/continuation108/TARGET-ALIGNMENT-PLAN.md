## خطة TRUNCATE منفصلة للموافقة
المثبت في107: public.order_items / authenticated=true، anon=false. RLS وتريغرات صفوف INSERT/UPDATE/DELETE ليست حماية لـTRUNCATE. احتمال حذف كامل محتوى الجدول مشروط بوجود مسار تنفيذ صالح وباقي قيود التنفيذ؛ لا نفترض نجاحه أو وجود HTTP endpoint.
مسارات التحليل المقترحة: اتصال SQL بدور يملك المنح أو يرثه؛ RPC ينفذ SQL أو dynamic SQL؛ دالة SECURITY DEFINER أو خدمة موثوقة تقبل مدخلات غير مقيدة؛ مسار إداري/استيراد. مجرد منح الجدول لا يثبت أن REST يتيح TRUNCATE.
حزمة التحقق المستقبلية: استخراج ACL والموروث وdefault privileges وEXECUTE/search_path والدوال المكشوفة وFK/dependencies وتريغرات statement الخاصة؛ تحديد حاجة تشغيلية لكل منح؛ اختبار الأدوار على نسخة منفصلة بصفوف اصطناعية فقط بعد تفويض. لا اختبار استغلال مستضاف.
المقترح المشروط: إزالة TRUNCATE غير الضروري من الدور الواسع ومن مصادر وراثته/منحه التلقائي، وقصر الصيانة الضرورية على دور ضيق ومسار مدقق. لا SQL تنفيذي في هذه الحزمة. موافقة منفصلة قبل أي تغيير، وفحص الاستيراد والصيانة والاعتماديات قبل اعتماده. لا تغييرات RLS عامة كحل جانبي.

6. حماية التاريخ: استرجاع نجاح تاريخي بالقراءة فقط للمفتاح والحساب نفسيهما مع التفويض الحالي؛ لا binding مصطنع ولا ادعاء تطابق مدخلات غير متاحة. تمييز الجديد عبر marker/binding؛ الجديد الناقص لا يتحول إلى تاريخي. ترحيل bindings102 فقط عندما تثبت مدخلاتها، وحفظ HMACv1 وسياق تكوينها.
7. ترتيب الحزمة المقترح بعد القبول: اعتماديات103 ثم104 ثم105 ثم106 أخيراً في وحدة انتقال محكومة مع الكتاب متوقفين؛ سياسات الموارد تأتي من قرار معتمد، لا fixture. التحقق من atomic DDL وإمكان المعاملة لكل خطوة قبل اختيار طريقة التنفيذ؛ لا ندعي أن كل إجراء تشغيلي ذرّي.
8. pre/post invariants: مقارنة الكائنات والمنح والتواقيع وإصدارات العقود؛ عدم تغير الطلبات التاريخية؛ عدم زيادة order/spend/loyalty دون عملية مقصودة؛ توازن القيود وعلاقاتها؛ عدم فقد bindings/closures أو إعادة فتح مفتاح؛ فحص RC/RU ودعم الاسترجاع ورفض RR/Serializable بلا آثار. تدقيق البيانات لاحقاً خاص ومصرح، لا ضمن108.
9. المصالحة: فقد ACK أو stale not_visible أو timeout أو40001/40P01/55P03 ليس تصريحاً بمفتاح جديد. إنهاء المعاملة القديمة والتحقق بالمفتاح الأصلي في معاملة مدعومة؛ لا retry كتابة أعمى. المحاولة المرفوضة نهائياً فقط تنتهي بإثبات خادمي موثق قبل محاولة جديدة.
10. rollback: إبقاء إنشاء الطلبات متوقفاً واستخدام مسار recovery-only المقبول؛ حفظ الحواجز والبصمات وإصدارات المفاتيح وحارس106 الداخلي. لا الرجوع إلى الكاتب القديم ثم فتحه. إعادة الترقية103→104→105→106 والتحقق قبل فتح الكتابة.
11. انقطاع وسط الانتقال: سجل مراحل وإصدار ومخرجات preflight خاص، تحقق من المرحلة الملتزمة قبل الاستئناف؛ لا إعادة تطبيق عمياء. restore لا يعيد الكتابة حتى مصالحة جميع الالتزامات بعد نقطة النسخة. تعذر الحسم يبقي النظام في الاسترجاع فقط.
12. إعادة فتح مقيدة فقط بعد قبول QA واكتمال بوابات الاختبار وموافقة تشغيل منفصلة؛ مع مراقبة الفشل والتكرار وآثار المال وخطة إيقاف. هذه الخطة لا تمنح تلك الموافقة.

1. اعتماد نطاق مرحلة التنفيذ المعزولة لاحقاً وأصحاب الصلاحية وقناة الأدلة والجلسات، وبيان نشر الكتّاب الخارجيين؛ التفويض الحالي للتخطيط فقط.
